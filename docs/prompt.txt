O arquivo openapi-api-acervo-digital.yaml contém o contrato OpenAPI 3.1 oficial do microsserviço api-acervo-digital e é a única fonte da verdade da API. A estratégia é obrigatoriamente API-First. Todos os controllers, DTOs e interfaces REST devem ser gerados a partir deste contrato utilizando openapi-generator. É proibido criar endpoints, payloads, parâmetros, respostas, schemas ou comportamentos que não estejam explicitamente definidos no OpenAPI. Controllers devem atuar exclusivamente como adapters de entrada, delegando a execução para casos de uso da camada Application. DTOs expostos pela API nunca podem vazar para o domínio.

O contrato OpenAPI define endpoints para upload de mídias, upload de documentos privados, consulta de mídias, consulta de documentos, aprovação, reprovação, publicação, bloqueio, arquivamento, definição de mídia principal, ordenação, geração de URLs assinadas, consulta de histórico, fila de aprovação, catálogos e relatórios de pendência. Tudo que estiver definido nesse contrato deve ser implementado de forma funcional, consistente e validável. Nada além do contrato deve ser inventado.

O arquivo contrato-operacional-para-swagger-openapi.txt define o contrato operacional obrigatório para implementação do Swagger e OpenAPI dentro do microsserviço. A implementação deve garantir que a documentação da API esteja completa, consistente e operacional em todos os ambientes suportados.

O runtime final deve expor os endpoints sob /api/v1. Os controllers não devem repetir /api/v1 em @RequestMapping. É proibido gerar rotas duplicadas como /api/v1/api/v1. O arquivo contrato-operacional-para-migrations-seeds.txt define o contrato operacional obrigatório para persistência e versionamento de banco de dados utilizando PostgreSQL e Flyway. O banco de dados deve ser dedicado ao microsserviço api-acervo-digital, seguindo o modelo 1:1. O Flyway deve ser o único mecanismo de versionamento de schema. As migrations estruturais devem ficar na faixa V001 até V099. Seeds de desenvolvimento devem ficar na faixa V101 até V199. Seeds devem executar exclusivamente no profile dsv e jamais em hml ou prd. As migrations devem ser imutáveis, incrementais, auditáveis, legíveis e determinísticas. Deve existir uma migration para criação do schema e uma migration por tabela. É proibido criar múltiplas tabelas no mesmo arquivo de migration.

O objetivo é gerar um microsserviço em Java 21 com Spring Boot 3.x que implemente exatamente um único Bounded Context: Acervo Digital. Este microsserviço deve controlar o ciclo de vida completo de imagens, vídeos e documentos da plataforma Via Fluvial. Ele deve permitir registrar uploads, manter arquivos em quarentena, impedir publicação automática de arquivos enviados por usuários externos, controlar aprovação e reprovação administrativa, publicar mídias aprovadas para uso público via CDN, bloquear mídias publicadas, arquivar mídias e documentos, remover logicamente itens do acervo, controlar documentos privados de barqueiros e embarcações, controlar validade documental, gerar URLs assinadas para acesso controlado, controlar finalidade, visibilidade, direito de uso e histórico de decisões administrativas.

O domínio deve estar no centro da arquitetura, completamente isolado de detalhes técnicos. A camada Application deve orquestrar casos de uso como registrar upload de mídia, registrar upload de documento privado, consultar item do acervo, listar mídias por entidade vinculada, listar documentos privados, aprovar mídia, reprovar mídia, publicar mídia, bloquear mídia, arquivar item, definir mídia principal, ordenar mídias de galeria, gerar URL assinada para documento privado, consultar histórico de decisões e consultar fila de aprovação. Ports devem definir contratos claros para persistência, armazenamento de objetos, geração de URL assinada, publicação em CDN, consulta a serviços externos e auditoria. Adapters devem implementar REST, persistência PostgreSQL, integração com storage/CDN, serialização JSON, logs estruturados e observabilidade, sempre respeitando a separação de responsabilidades.

O domínio deve conter entidades e comportamentos reais. Entidades como AcervoItem, Midia, DocumentoPrivado, AcervoArquivo, AprovacaoAcervo, DireitoUsoMidia, VinculoEntidade, HistoricoAcervo, TipoDocumento e DocumentoEntidade devem representar conceitos de negócio e não apenas estruturas anêmicas. Value Objects como MediaPublicKey, OwnerPublicKey, BoatPublicKey, EntityReference, ObjectPath, CdnUrl, MimeType, FileSize, FileHash, MediaPurpose, Visibility, AcervoStatus, ApprovalStatus, DocumentStatus, RejectionReason, UsageRights e ValidityPeriod devem proteger invariantes, validar dados e impedir estados inválidos.

As transições de estado do acervo devem ser explícitas e validadas. Status como RASCUNHO, ENVIADO, EM_QUARENTENA, AGUARDANDO_APROVACAO, APROVADO, REPROVADO, PUBLICADO, BLOQUEADO, ARQUIVADO, REMOVIDO e EXPIRADO devem obedecer às regras negociais documentadas. Somente itens com status PUBLICADO e visibilidade PUBLICA podem aparecer no site, fluxo de venda, galeria pública ou CDN pública. Documentos privados nunca devem ser publicados em CDN pública. Mídias enviadas por barqueiros, agências ou usuários externos nunca devem ser publicadas automaticamente.

A aprovação deve registrar quem aprovou, quando aprovou, qual item foi aprovado, qual finalidade foi aprovada e qual visibilidade foi autorizada. A reprovação deve exigir motivo obrigatório. A publicação deve validar que o item está aprovado, possui finalidade compatível, possui visibilidade pública, não está bloqueado e não possui pendência de direito de uso quando aplicável. A publicação não deve ser tratada apenas como movimentação de arquivo; ela representa uma decisão de negócio controlada.

O controle de direito de uso deve permitir registrar origem da mídia, responsável pelo envio, declaração de direito de uso, autorização para galeria, autorização para fluxo de venda, autorização para site, autorização para marketing, autorização para redes sociais, autorização para apresentações, validade da autorização e documento de autorização vinculado, quando necessário. Mídias com pessoas identificáveis não devem ser usadas para marketing amplo sem autorização específica. Mídias aprovadas para galeria não devem ser automaticamente autorizadas para campanhas de marketing.

Os documentos privados devem ser controlados de forma separada das mídias públicas. Documentos de barqueiros e embarcações devem possuir visibilidade privada ou restrita, nunca pública. O microsserviço deve controlar documentos como CNPJ, CPF quando aplicável, contrato social, procuração, autorização de operação, documento da embarcação, licença, vistoria, seguro, norma de segurança, certificado, termo de responsabilidade e autorização de uso de imagem. Documentos podem possuir data de emissão, data de validade, órgão emissor, número do documento, status documental, data de aprovação e responsável pela análise. Documentos vencidos, reprovados ou ausentes podem impactar a disponibilidade do barco para venda, mas a decisão final de bloqueio operacional deve respeitar a separação com os domínios responsáveis, como Embarcações, Compliance e Administração.

O Acervo Digital não deve assumir regras de outros domínios. Ele não deve cadastrar barqueiro, cadastrar agência, cadastrar embarcação, definir capacidade do barco, criar viagem, vender passagem, calcular tarifa, processar pagamento, autenticar usuário, definir política comercial ou substituir o domínio de compliance. Ele pode guardar arquivos vinculados a essas entidades, mas não deve ser dono da regra principal dessas entidades. Integrações com outros domínios devem ocorrer por ports out e adapters, nunca por acoplamento direto.

O microsserviço deve ser totalmente funcional e pronto para produção, incluindo perfis de ambiente dsv, hml e prd, configuração externa por variáveis de ambiente, tratamento de erros no padrão RFC 7807, logs estruturados em JSON com X-Correlation-Id, persistência em banco dedicado com migrations versionadas, seeds sintéticos apenas em desenvolvimento, actuator, métricas, healthcheck, segurança plugável, Swagger UI funcional, OpenAPI runtime e YAML estático versionado.

As variáveis de ambiente devem permitir configurar banco de dados, profile ativo, modo de segurança, integração com storage, buckets, CDN e limites de upload. O projeto deve aceitar configurações como bucket de quarentena, bucket público de mídia, bucket privado de documentos, URL base da CDN, tamanho máximo de imagem, tamanho máximo de vídeo, tamanho máximo de documento, tipos MIME permitidos e modo de aprovação obrigatória. Nenhuma credencial real, arquivo .env real, chave de service account ou segredo deve ser commitado no repositório.

Devem existir testes unitários de domínio sem Spring, testes de casos de uso, testes de adapters REST, testes de persistência com Testcontainers e PostgreSQL e testes que garantam aderência estrita ao contrato OpenAPI. A cobertura mínima de testes deve ser de 80% nas camadas de domínio e aplicação, com falha automática do build caso a meta não seja atingida. Testes devem cobrir transições de estado, aprovação, reprovação, publicação, bloqueio, arquivamento, validação de finalidade, validação de visibilidade, controle de direito de uso, documentos vencidos, URL assinada e acesso a documentos privados.

O projeto deve gerar Dockerfile, Docker Compose, Makefile, configuração Maven, Maven Wrapper, estrutura de pastas hexagonal, arquivos de configuração por ambiente, migrations Flyway, seeds de desenvolvimento, testes automatizados, README e documentação operacional mínima. O Docker Compose deve subir a API e o PostgreSQL dedicado com os nomes, portas e variáveis reais do projeto. O Makefile deve conter comandos para gerar fontes OpenAPI, rodar a aplicação, testar, buildar, empacotar, subir e derrubar a stack, verificar health, verificar Swagger, verificar OpenAPI, acessar shell da aplicação e acessar shell do banco.

É expressamente proibido criar código mockado, placeholders artificiais, domínio anêmico, classes utilitárias genéricas, dependências técnicas no domínio, lógica de negócio em controllers, entidades JPA vazando para o domínio, DTOs de API vazando para o domínio, mistura de responsabilidades entre camadas, endpoints fora do OpenAPI, alteração arbitrária de nomes, portas, banco, schema ou pacote base, ou qualquer desvio das regras definidas nos arquivos da pasta docs.

O resultado final deve ser um repositório completo, funcional, testável, evolutivo e fiel ao domínio de Acervo Digital, pois este serviço será responsável por garantir governança, segurança, rastreabilidade e publicação controlada de imagens, vídeos e documentos da plataforma Via Fluvial.
